你在接手一个面向客服运营团队的 AI 工单分诊 API。最近一次紧急改动后，值班同学反馈这个服务已经不适合作为稳定的辅助链路：不同运行模式下返回结果前后不一致，批量请求有时拿不到完整结果，部分工单的人工升级与知识建议也不再可靠。你需要在不改变业务边界的前提下修复现有服务，让它重新满足生产集成要求。

输入数据在 `/app/workspace/`：

- `service/`：现有 Node.js / TypeScript HTTP 服务代码，包含单条分诊、批量分诊、复核建议等对外链路。
- `data/tickets/`：真实风格工单样本，包含 in-domain 与 out-of-scope 文本、语言、渠道和优先级相关字段。
- `data/contracts/`：分诊输出合同、字段枚举、provider 适配形态与相关规则。
- `data/policies/`：队列映射、人工升级规则、知识建议约束和批处理行为要求。
- `data/sandbox_cases/`：sandbox 模式下的本地 case 与回包样例。
- `scripts/`：启动、重置和基础自检脚本。

环境里还包含以下基线目录：

- `/services/provider-sim/`：本地下游 provider simulator，属于环境基线的一部分，不得编辑。

你的任务：

1. 修复单条分诊、批量分诊、复核建议三条 HTTP 链路，使服务重新满足现有对接方依赖的交付合同；不要通过新增一套平行接口来规避现有问题。
2. 保证单条与批量请求在现有不同运行模式下都返回稳定、完整、可机器处理的结果；同一批请求中的各条工单不能静默丢失，也不能把失败伪装成成功。
3. 保留现有业务含义和输出能力，让队列、意图、推荐操作、引用证据和人工升级原因继续基于真实输入数据与现有规则产生；当部分信息无法命中时，也必须保持返回结构稳定。
4. 当 live 链路拿到的下游结果不完整、不可解析或不可信时，不要把同一工单改写成另一套业务结论；需要继续依据仓库内现有系统事实返回稳定结果。
5. 保留并修复真实运行链路，继续使用现有启动方式、sandbox 数据、本地下游 provider simulator 和现有 API 路径；不能把任务改写成离线脚本、静态结果生成或人工整理流程。
6. 保持现有业务边界不变，继续使用仓库内现有数据文件作为系统事实来源。
